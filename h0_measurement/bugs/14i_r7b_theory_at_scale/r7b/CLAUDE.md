# 14i_r7_theory_at_scale/r7b — R7b: the deployed design (the single store), its theory

Read `STATUS.md` first, then `theory_r7b.md` (what R7b tests, why the single store's forms are valid, the predictions).
R7b's spec is `../../14h_theory/RESEARCH_PLAN.md` §4 "R7b" and §8 (the handoff); R7a's folder rules are `../CLAUDE.md`.

## Why a subfolder (not `_r7b` files beside R7a's)
R7a's driver hashes every top-level `*.py` of `14i_r7_theory_at_scale/` into each block's code manifest
(`../run_r7.py:code_manifest`, a non-recursive glob), and R7a's reader flags blocks whose manifests differ
(`code_manifests_identical`). R7a's blocks start at different times, so adding or editing any top-level `.py` while R7a
has jobs queued or running would taint R7a's read. Everything of R7b's lives here; the parent folder is not touched.

## Isolation (user, 2026-10-11 and 2026-10-12): development and exploration stay in this folder
- **Nothing outside `r7b/` is edited.** Not R7a's files in `..` (pinned: `../findings/R7a_code.sha256`), not
  `../../14h_theory/`, `../../14h_methodology_improve/`, `sievelib/`, `run_h0.py`, `run_r8.py`.
- **Nothing here imports `../../14h_theory/`.** What R7b needs from it is copied into `store_r7b.py` / `cert_r7b.py` with
  the source and its sha256 named; parity is checked against frozen fixtures (`fixtures/`, generated by a script kept
  outside, whose source is in `fixtures/README.md`).
- **R7a's modules are imported read-only** from `..` (`cert_r7`, `tier_r7`): R7b's bounds are R7a's code re-bound to a
  per-coordinate `exact_rows` (`cert_r7b._relink`), never copies of it, and never patched in place.
- **R6's run-time chain is imported read-only.** `run_r7b.py` wraps `../../14h_methodology_improve/run_s1h5` and its
  chain (`s1h5_lib`, `tasks_s1h4`, Stage 1g, `run_r8`, `sievelib`) as `../run_r7.py` does. It swaps module attributes for
  the run and restores them, and never edits a file.
- **Read-only data:** R7a's captured views (`../.views/`), R6's per-unit results (`h0_measurement/results/r14s1h_h6*`, for
  the power analysis only), `sievelib` (the Lloyd-Max codebook, rotations, FP8, KIVI).
- **Module names end in `_r7b` and are unique** across every folder on `sys.path`.
- Exploration outputs go to `findings/` here; new view captures, if ever needed, to `r7b/.views/`; temporary files to the
  scratchpad.

```bash
../../../../.venv/bin/python -u explore_r7b.py summary      # and: power, power-mv, cost
```
One process per step: login nodes cap a process at 3,600 s of CPU time, and other sessions' CPU jobs share the node
(CPU time inflates under contention; keep `bias` parts at ≤ 20 draws with 4 threads). `cp`/`rm` are aliased to `-i`:
use `command cp -f` / `/bin/rm -f` in scripts. Don't modify the shared `.venv`.

Nothing here is a GPU run yet. The run side is built and the user's decisions (`plan_r7b.md` §8) are applied
(2026-10-12). It freezes on the user's go-ahead (`--freeze`), then goes out stage by stage on Trillium and Rorqual
(`plan_r7b.md` §9: the order, the cluster split, the sync lists); never re-pin once a job exists. The driver
smokes need a CPU node (the login node's CPU-time cap is too short): run `test_run_r7b.py` from a Slurm CPU job. GPU jobs
are submitted only when the user asks, from trig-login01.
